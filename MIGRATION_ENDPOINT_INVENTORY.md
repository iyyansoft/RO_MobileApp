# Existing Express endpoint inventory and target mapping

This inventory contains **66 concrete `/api` method/path routes across 65 Express registration declarations**. The difference is the legacy dealer deletion handler, which registers two paths (`/api/admin/users/:id` and `/api/admin/dealers/:id`) in one Express declaration; both are listed separately below. The static `/admin` web routes and catch-all are not API routes.

All 66 concrete `/api` paths are still registered in and served by Express. A row naming a local Supabase adapter/function is an un-deployed, default-off pilot; other Supabase target text is a recommendation, not an implementation. No route is retired or production-verified. Static Admin Web routes are listed separately at the end.

## Dealer-owned data migration status

The address, cart, order-history/detail, rewards-history, support-ticket, and profile read/edit client paths are prepared behind `USE_SUPABASE_DEALER_DATA` (default `false`) and require `USE_SUPABASE_AUTH=true` plus a valid Supabase session. The Express endpoints remain the default fallback. Checkout/order creation, payment, invoices, password operations, admin, and shop operations remain server-side. Staged SQL drafts are under `supabase/staging/`; the prior combined drafts are archived under `supabase/drafts/unreconciled/` and have not been applied remotely. Stages 001–004 have disposable local PostgreSQL harness coverage; 001, 002, and 004 also passed local Supabase Auth/PostgREST/RLS integration. Hosted project compatibility remains unverified.

Inventory checked in `server.js`, `order_checkout.js`, and `shop_routes.js`. Responses are JSON (`success`, entity/list, or `error`) except the static `/admin` routes. Table names below are verified from the route SQL and schema; database access is through the existing PostgreSQL pool. “Auth now” describes route middleware in source, not a recommended security posture.

## Other routes and external services

- Static GET `/admin`, `/admin/*` routes serve the legacy web preview; they are not API endpoints. The current Flutter Web admin entrypoint is separate.
- External services found: SMTP via Nodemailer for OTP/reset messages; Razorpay API for order creation/payment verification/capture; Google OAuth library for Google sign-in; local filesystem uploads under `web_preview/uploads`; Puppeteer for invoice/PDF output where configured.
- No separate payment, invoice, support, reward, or reports API route was found beyond those listed above; those features are returned/processed by the listed user/admin order routes.
