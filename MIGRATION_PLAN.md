## Scope and safety

This project already stores business data in Supabase PostgreSQL through the Node.js `pg` pool in `db.js`. This migration is about moving suitable operations away from Express while retaining the same database and records. The migration is opt-in: the Flutter app continues to use Express unless `SUPABASE_URL` and `SUPABASE_ANON_KEY` are supplied at build time and `USE_SUPABASE_AUTH=true` is set. No migration is applied by the app or backend.

Do not expose a Supabase service-role key or PostgreSQL password in Flutter/browser code. The SQL below is additive. Review it and take a database backup before applying it in the Supabase SQL Editor. Do not run it against production until reviewed and approved.

## Admin Web migration plan (catalog CRUD pilot prepared locally; no cutover)

`lib/admin_web_main.dart` uses `AdminRepository`; that repository authenticates and sends every dashboard request to Express. The web dashboard currently loads dashboard statistics, analytics, dealers, products, categories, orders, and shop employees. The UI derives Payments and Invoices from orders, and its product/bulk/category forms post to Express. `server.js` and `shop_routes.js` additionally provide dealer status/deletion, order status, shop assignment/employee activation, enquiries, notifications, and refund adjustment routes. The admin image forms still use the Express upload path. This project has no verified Supabase Auth admin provisioning path yet.

Recommended staged replacement:

1. Provision/revoke admin identities through a controlled trusted operation and store the authorization role only in Supabase `app_metadata`; verify denied dealer/pending identities and session revocation. Do not accept admin role from Flutter metadata.
2. Migrate dealer approval/status through the local `admin-dealer-approval` Edge Function pilot, then verify role denial, ambiguity handling, persistence, pending-dealer session blocking, and browser reload in isolated staging. Its separate flag remains false and Express is the default.
3. The dealer directory `GET /api/admin/dealers` now has a local read-only Edge Function pilot behind `USE_SUPABASE_ADMIN_DEALERS=false`. Verify safe projection parity, pagination, live schema, Auth authorization, and browser rendering on isolated staging before enabling.
4. Add per-feature default-off admin migration flags and a server authorization layer (`auth.getUser` plus `app_metadata.role == admin`). Keep direct table grants/RLS closed to browser clients and make privileged reads/writes go through server-side functions.
5. Move dashboard stats, analytics, product/category/order reads to bounded, read-only admin Edge Function actions. Verify aggregate parity and avoid returning password hashes, OTPs, service data, or unneeded purchase-price values.
6. Move product/category create/update and stock management with server validation, SKU uniqueness, safe category references, and an audited deactivate policy. Add bulk imports as a whole-batch validated operation with duplicate detection and atomic result semantics.
7. Create/verify Storage and migrate product/category images from local Express disk only after URL inventory and object checks; upload authorization must use the same verified admin identity.
8. Migrate dealer deletion, order/payment status, invoice metadata, and shop employee/assignment/enquiry/notification/refund operations separately. Keep payment evidence, COD cash collection, shop assignment, delivered quantities, and refund state server-validated and transactional.
9. Run browser integration tests for admin role denial/revocation, every section and mutation, uploads/imports, order/payment/refund integrity, plus reload persistence. Remove the Express Admin Web path only after parity and rollback acceptance.

### Local bulk Excel/CSV import pilot (2026-10-27)

- Audited the existing Flutter Web parser/preview, `POST /api/admin/products/bulk`, and its row-by-row PostgreSQL insert contract. Express currently preloads SKUs/categories, skips invalid and duplicate rows, inserts each accepted row independently, and returns `imported`, `skipped`, and `importedCount`; therefore a database failure can leave a partial batch.
- Added server-side canonical field/alias handling and validation for names, SKU format, category references, numeric price/stock types and ranges, two-decimal currency precision, bounded fields, MOQ, image data, specs/features, duplicate rows, and existing SKUs. The SQL draft rejects null/malformed JSON payloads and only treats the SKU index conflict as a skippable duplicate; other uniqueness failures abort the transaction. The client preview adds duplicate-header and matching price/SKU/MOQ checks, but the Edge Function/RPC remains authoritative.
- Added a `bulk_import_products` action to the admin-only Edge Function. It limits a batch to 200 rows and the request body to 8 MiB, resolves categories from PostgreSQL, validates product images, and keeps the existing product fields (purchase/dealer/MRP prices, stock/min stock, MOQ, description, images, JSON specifications/features, badge/rating, status, applications).
- Added `supabase/drafts/unreconciled/20261030_admin_bulk_import.sql`, a local-only `SECURITY DEFINER` RPC and request-fingerprint ledger. One RPC transaction inserts the accepted rows and stores the response; identical retries by the same verified admin return the prior result, while duplicate SKUs are skipped and never overwrite existing products. Any other database failure rolls back all inserts and the ledger row. No live SQL was executed.
- Bulk image data URLs use content-addressed Storage paths so retries do not create duplicate objects. Storage itself is not transactional with PostgreSQL; if the database transaction fails after upload, unused objects may remain for later cleanup. Existing URL/path image references are retained.
- Flutter Web routes the existing `products/bulk` call to the Edge Function only when `USE_SUPABASE_ADMIN_BULK_IMPORT=true` and a verified Supabase Auth admin session is active. The independent flag defaults to false; Express remains the active default/fallback. The UI recognizes replay responses and does not claim that duplicate records were newly imported.
- Tests cover server normalization, invalid field types/prices, duplicate rows, admin denial, CRUD/bulk action dispatch, request size, sanitized failures, idempotency SQL safeguards, and Flutter request routing. PostgreSQL transaction behavior, Edge Runtime, Storage, and browser integration remain unverified.

Admin migration is not complete. Express remains the working admin backend and source of truth during this plan. The detailed route-to-feature mapping and unverified assumptions are in `SUPABASE_FEATURE_MIGRATION_CHECKLIST.md`.

## Limitations and complexity

- This change is groundwork, not a completed production cutover. Database SQL, Auth email, redirect, Storage, and staging/end-to-end tests require manual Supabase configuration and approval.
- Existing users do not automatically acquire Supabase Auth identities. They must be linked through a verified email identity, or use a separately designed password-reset/account migration process.
- Supabase free-plan limits, inactivity pausing, email delivery restrictions, storage/egress quotas, and Edge Function quotas can change; check the current Supabase/Vercel plan pages before launch. Free hosting is not guaranteed permanently.
- At the time of this implementation, Supabase Free lists two active projects, 500 MB database, 1 GB file storage, 5 GB uncached egress, 5 GB cached egress, and pauses low-activity free projects after about seven days. Its built-in Auth email service is best-effort and currently limited to two emails per hour and authorized recipients; production email OTP needs custom SMTP. Edge Functions on Free have a 150-second wall-clock limit and 2-second CPU time per request. These limits may change.
- Vercel Hobby is restricted to personal/non-commercial use, so it is not a suitable free host for this wholesale business admin dashboard under the current terms. Cloudflare Pages is a more suitable static Flutter Web candidate; its current Free limits include 500 builds/month, 20,000 files/site and 25 MiB/file. Static assets are free/unlimited; any Pages Functions use Workers quotas. Confirm current plan terms and limits before launch.
- Auth/RLS + token bridge: medium/high; catalog: low; addresses/cart/history/rewards/support: medium; storage migration: medium; payment/checkout and shop/admin workflows: high and should remain trusted-server operations during this migration.
